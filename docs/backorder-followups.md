# One-time follow-ups after generic notices

Successful manual Shipping Delay sends and automatic initial notices can enroll items, only after the initial Klaviyo event is accepted and its `NotifyDockEmailHistory` row is saved. The locked order creation cutoff applies to both. Existing history is never backfilled and no order/catalog search is performed by the scheduler.

Enrollment requires a Shipping Delay email with no global date, an included product using the generic message, and an outstanding order line from any vendor with Backorder / Build to Order / Built to Order availability. Each record identifies the shop, order, line item, variant, original availability type and initial email history. An item is enrolled only once per order. The recipient comes from the original manual email, including an address typed into To.

The Backorder order tag is required at enrollment/initial automatic sending. Removing it afterward intentionally does not stop daily checks. Fulfillment, cancellation and current product availability still stop ineligible items without sending. Automatic payloads match exact line/variant identities; manual SKU-only payloads enroll only when the SKU maps unambiguously to one variant.

Backorder records wait for a valid strictly future `custom.product_availability_date`. Built to Order records wait for nonblank plain text in `custom.build_to_order_message`. Missing information remains pending. Cancelled, fulfilled, removed or reclassified items stop without sending. Ready items from the same initial email are grouped into one follow-up. Other waiting items can receive their own one-time follow-up on later days. Each item is completed after its first follow-up; later date changes do not restart it. Tracking ends for the order when no pending or queued items remain.

`.github/workflows/backorder-followups.yml` schedules one daily run at 16:00 America/Los_Angeles, including daylight saving changes. No five-minute timers remain. The workflow calls the endpoint in pages until due tracked work is drained, with a 45-minute limit. The endpoint refuses product checks outside the 4 p.m. Pacific hour. GitHub schedules may start late, so 4:00 is the scheduled start, not an exact delivery guarantee. Failed sends retain their stable payload for the next daily check; missing information also waits until the next day. The former test-time override is not configured in production.

`NOTIFY_DOCK_FOLLOWUP_ENABLED=true`, `NOTIFY_DOCK_FOLLOWUP_SHOPS` (exact shop allowlist) and `NOTIFY_DOCK_FOLLOWUP_SECRET` are required. The scheduler secret is stored in production Vercel environment variables and the production GitHub repository's Actions secrets. The workflow is restricted to DieselPowerProducts/NotifyDock. The production shop is fbgure-nn.myshopify.com. No scheduler is enabled in previews by default. Set enabled=false and redeploy to stop enrollment and processing.

Before contacting Klaviyo, the database stores a batch with its exact payload, recipient, metric and stable event ID. After the final eligibility check it also persists an attempt timestamp; a failed write blocks the provider call. Retries reuse the saved ID and payload. Changes to a possibly attempted batch hold it for review. A batch proven never attempted can be retired and its items resolved independently, preserving eligible companions instead of discarding the entire group. Legacy batches are treated as possibly attempted. A shop lease prevents concurrent workers. Accepted batches and items remain completed and are never sent again. Klaviyo acceptance is not proof of inbox delivery; delivery tracking remains in email history.

Pagination retrieves complete initial-email groups, so the 100-item seed page cannot divide one order's same-day updates across separate emails.

Verification: `node --test scripts/verify-backorder-followups.mjs`, `node --test scripts/verify-backorder-prefill.mjs`, `node scripts/verify-composer-dates.mjs`, `npm run build`.

The all-vendor initial-email cutoff is separately locked in `NotifyDockAutomationPolicy.initialStartAt` and `NOTIFY_DOCK_AUTOMATION_INITIAL_START_AT`. It is September 30, 2026 at 4:20 p.m. Pacific (`2026-09-30T23:20:00Z`). The original `startAt` remains unchanged for existing follow-ups and manual prefill. Missing or mismatched initial settings block new automatic initial sends. No historical scan or tracking backfill is introduced.

Each worker attempt loads one Shopify snapshot per order and uses it for both eligibility and email content. There is no second read immediately before submission. A later retry or daily check reads fresh data once; an ETA added after today’s undated snapshot is picked up at the next daily check. Line-item pagination, when needed, is part of loading that snapshot.

Backorder ETA freshness: initial dates on or before the store’s current calendar day use the generic message and enroll for tracking. Daily checks require an ETA strictly after the checking day; today or older keeps the item pending without another generic email. Built to Order messages remain plain text and retain their existing behavior.

Cutoff boundary for new enrollment: both manual and automatic initial emails must use an order created on/after the new initial cutoff before new follow-up tracking can be saved. Older orders can only finish pending/batched tracking that was created before that cutoff, with matching shop/order identity. Both the daily worker and final automatic sender check this evidence; #969960’s existing September 28 record is preserved.
